## Environment integration evidence and boundary

The installed T3 server bundle was inspected read-only. Its supported public descriptor is `GET /.well-known/t3/environment`. Authenticated read endpoints include `GET /api/orchestration/shell`, `GET /api/orchestration/threads/:threadId`, and bounded/history/transcript forms. WebSocket RPC `peerLinks.list` exposes true linked IDs, labels, URLs and status. Linking goes through T3's official peer OAuth/pairing flow and the Linked environments setting; Lucid's existing local bearer cannot authenticate a remote environment.

`peer_environment_links` exists in this local database, but the official list returned no links during the audit. A correct implementation must use an actual linked environment plus its own authenticated read/operate session, scope all thread and project identities by environment, maintain separate persisted camera/room/selection state, and route every action, attachment and subscription to that same environment. A disconnected building should keep honest connection state and preserved selection. It must never substitute local projects into an Ares-labelled building or send an action to the wrong machine. Connection setup requires the supported T3 connection UI/card, not a chat request for a secret.

The new environment service was read against the actual installed server: it returned the real `Tim-PC` descriptor as reachable and no linked environments. `node scripts/verify-environments.cjs` covers source errors, duplicate entries, origin sanitization, cached concurrent reads and rejecting unknown/remote action targets.
